# DolphinScheduler 代码检索工具需求

## 概述

基于 DolphinScheduler 中实际运行的任务代码，构建类似 grep 的检索工具，用于查找分散在不同项目、工作流中的任务代码。

---

## 数据模型

### 数据源

| 数据库标识符 | 实际数据库名 | 表名 | 说明 |
|-------------|-------------|------|------|
| mysql_137 | data_factory | metadata_ds_table_lineage | DS表级元数据信息 |

> 💡 测试环境使用 `mysql_137`，生产环境如有变化再更新此文档

### 核心字段映射

| 字段 | 类型 | 说明 |
|------|------|------|
| project_name | varchar(200) | 项目名称 |
| process_name | varchar(500) | 工作流名称 |
| process_status | varchar(100) | 工作流状态：0-下线，1-上线 |
| task_name | varchar(500) | 任务名称 |
| task_status | varchar(100) | 任务状态：0-未启用，1-启用 |
| from_database_table | varchar(200) | 来源库表（多个用逗号分隔，已脱敏占位符） |
| to_database_table | varchar(200) | 去向库表（多个用逗号分隔，已脱敏占位符） |
| lineage_type | varchar(100) | 血缘类型：SQL / SHELL_SQL（两者存储的都是解析后的 SQL，仅用于区分来源） |
| sql_code | longtext | SQL代码文本（含占位符如 ${var}, @{变量}）|

> 💡 **数据时效性**：表中数据由定时任务每 8 小时更新一次，非实时同步。仅返回任务的最新版本，不涉及历史版本追溯。

### 任务状态判定

| process_status | task_status | 最终任务状态 |
|----------------|-------------|-------------|
| 1 (上线) | 1 (启用) | **已上线** |
| 1 (上线) | 0 (未启用) | 未上线 |
| 0 (下线) | 1 (启用) | 未上线 |
| 0 (下线) | 0 (未启用) | 未上线 |

即：**process_status=1 且 task_status=1 = 已上线**，其他均为未上线。

## 缓存机制

### 设计目标

由于数据更新频率较低（每 8 小时），采用**启动时全量加载 + 内存缓存**策略，避免每次查询都连接数据库，提升响应速度。

### 内存数据结构

```python
# 核心缓存字典：以 code_path 为唯一键
task_cache: Dict[str, Dict] = {
    "/ds/ODS/日报工作流/用户表同步": {
        "project_name": "ODS",
        "process_name": "日报工作流",
        "task_name": "用户表同步",
        "process_status": "1",
        "task_status": "1",
        "lineage_type": "SQL",
        "from_database_table": ["db.table_a", "db.table_b"],
        "to_database_table": ["db.table_c"],
        "sql_code": "SELECT ...",
        "sql_lines": [...],  # 按行拆分的代码数组
        "任务状态": "已上线"
    },
    ...
}

# 辅助索引（加速特定查询）
by_project: Dict[str, List[str]] = {
    "ODS": ["/ds/ODS/日报工作流/用户表同步", ...],
    "DWH": [...],
}
by_from_table: Dict[str, List[str]] = {
    "table_a": ["/ds/ODS/...", "/ds/DWH/..."],
}
by_to_table: Dict[str, List[str]] = {...}
```

### 初始化策略

| 触发时机 | 操作 |
|---------|------|
| 服务启动时 | 自动加载全量数据到内存缓存 |
| 首次调用工具时 | 懒加载（全量查询一次数据库） |
| 提供手动刷新接口 | 支持管理员手动触发缓存更新 |

### 缓存更新机制

1. **定时刷新**：服务启动后每 8 小时自动重新加载
2. **手动刷新**：提供 MCP 工具或 API 接口供管理员手动刷新缓存
3. **启动刷新**：服务重启时自动加载最新数据

> ⚠️ 注意：缓存更新期间，服务可能会有短暂阻塞。建议在低峰期进行自动刷新，或提供优雅的热重载机制。

### 优势分析

| 对比项 | 原方案（每次查询） | 新方案（内存缓存） |
|-------|-------------------|-------------------|
| 响应速度 | 数百毫秒~秒级 | 毫秒级 |
| 数据库压力 | 每次查询都连接 | 仅初始化/刷新时连接 |
| 并发能力 | 受限于数据库连接数 | 无连接瓶颈 |
| 数据一致性 | 实时 | 存在 8 小时延迟窗口 |

## 工具一：datafactory_sql_search

对标 grep 的代码检索工具。

### 功能列表

| # | 功能 | 说明 |
|---|------|------|
| 1 | 正则匹配 | 输入正则表达式，输出匹配到的代码 |
| 2 | 精确任务路径 | 通过完整 code_path 指定单个任务 |
| 3 | 大小写不敏感 | 默认忽略大小写 |
| 4 | 上下文参数 | 支持 `before`、`after` 参数，输出匹配行前后N行 |
| 5 | 状态过滤 | 支持 `code_status` 参数，默认只搜索"已上线"的代码 |
| 6 | 起止行读取 | 通过 `start_line`、`end_line` 直接读取连续代码，不执行正则 |
| 7 | 结果限制 | 单次最多返回100个匹配行，超出时截断并提示 |

### code_path 参数说明

将项目、工作流、任务的层级关系封装为路径格式，对 AI 隐藏内部结构。`sql` 只接受完整任务路径。

| 格式 | 示例 | 含义 |
|-----|------|------|
| /ds/项目名/工作流名/任务名 | /ds/ODS/日报工作流/用户表同步 | 精确到单个任务 |

> 匹配规则：
> - code_path 首尾空格会被去除，末尾斜杠允许存在
> - 不完整路径、项目路径或工作流路径会返回错误，不会进行模糊扫描
> - 需要模糊发现任务时，应先调用 datafactory_task_info

### 数据规模参考

| 指标 | 数值 |
|------|------|
| 项目数量 | 约 30 个 |
| 任务节点总数 | 约 5000 个 |
| 单任务平均代码行数 | 几百行 |
| 单任务最大代码行数 | 几千行 |


### 请求参数

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|-----|------|------|--------|------|
| pattern | string | 否 | 空 | 正则表达式；为空时返回该任务的 SQL 结构概览 |
| code_path | string | 是 | - | 完整且精确的任务路径 |
| before | int | 否 | 0 | 匹配行前的行数 |
| after | int | 否 | 0 | 匹配行后的行数 |
| code_status | string | 否 | "已上线" | 状态过滤：已上线/未上线/全部 |
| page | int | 否 | 1 | 页码 |
| page_size | int | 否 | 50 | 每页条数 |
| start_line | int | 否 | - | 起始行号，和 end_line 同时填写时读取代码 |
| end_line | int | 否 | - | 结束行号，包含该行；单次最多读取100行 |

### 返回格式

```json
{
  "matches": [
    {
      "code_path": "xxx",
      "行号": 11,
      "代码片段": "select * from table..."
    }
  ],
  "pagination": {
    "page": 1,
    "page_size": 50,
    "total": 100,
    "total_pages": 2
  }
}
```

当 pattern 为空时，返回 fallback=true、原因说明以及该任务的 overview，不返回 SQL 原文。

## 工具二：datafactory_task_info

任务详情查询工具。

### 功能列表

| # | 功能 | 说明 |
|---|------|------|
| 1 | 路径查询 | 通过 code_path 精确或模糊匹配任务 |
| 2 | SQL结构概览 | 返回语句、输入输出表、CTE及其行号，不返回固定代码片段 |
| 3 | 代码行数 | 返回完整代码的总行数 |
| 4 | 表清单提取 | 自动识别输入表和输出表 |

### 请求参数

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|-----|------|------|--------|------|
| code_path | string | 否 | - | 路径筛选，支持精确或模糊匹配（如 `/ds/*/*/决策`） |
| from_table | string | 否 | - | 输入表名称筛选，支持模糊匹配 |
| to_table | string | 否 | - | 输出表名称筛选，支持模糊匹配 |
| page | int | 否 | 1 | 页码，从1开始 |
| page_size | int | 否 | 20 | 每页任务数，最大50 |

> 注：三个参数至少填写一个，支持任意组合筛选（AND 逻辑）。

### 返回格式

```json
{
  "tasks": [
    {
    "code_path": "/ds/ODS/日报工作流/用户表同步",
    "任务类型": "SQL",
    "代码行数": 500,
    "任务状态": "已上线/未上线",
    "输入表清单": ["db.table_a", "db.table_b"],
    "输出表清单": ["db.table_c"],
    "sql_overview": {
      "parse_ok": true,
      "statement_count": 1,
      "statements": []
    }
    }
  ],
  "pagination": {
    "page": 1,
    "page_size": 20,
    "total": 35,
    "returned": 20,
    "total_pages": 2,
    "has_previous": false,
    "has_next": true
  },
  "hint": "共35条任务，本页展示20条（第1/2页）。如需继续查看，请保持筛选条件不变并传 page=2。"
}
```

> 注：返回中的 `code_path` 即任务的唯一标识，可用于后续关联查询。
> `hint` 会告诉 agent 当前总数、本页展示数和下一页调用方式；overview 只为当前页任务生成。

### 表清单说明

- **来源**：「直接从数据库字段读取，不做二次解析」
- **输入表**：`from_database_table` 字段，格式如 `db.table1,db.table2`
- **输出表**：`to_database_table` 字段，格式如 `db.table1,db.table2`
- 返回时需拆分逗号为数组格式

## 边界情况处理

| 场景 | 处理方式 |
|------|---------|
| sql_code 为 NULL | 返回空字符串，跳过该记录 |
| from/to_database_table 为 NULL | 返回空数组 |
| 无匹配结果 | 返回 `tasks=[]`，并在 pagination 中返回 `total=0` |
| task_info 页码超出范围 | 返回空 tasks，并提示合法页码范围 |
| sql 的 code_path 不完整 | 返回错误，提示先通过 task_info 获取完整任务路径 |
| 正则语法正确但匹配不到任何内容 | 返回空结果（不同于语法错误） |
| 正则语法错误 | 返回错误提示，说明原因及具体位置 |
| before/after 超出行数范围 | 只返回实际存在的行数 |
| before/after 同时使用且匹配行相邻 | 允许重叠返回，不做去重（保留完整上下文） |
| 所有筛选参数均未填写 | 返回错误提示"请至少填写一个筛选条件" |
| code_path 参数带有前后空格 | 自动 trim() 后再做匹配 |
| sql 的 pattern 为空 | 返回该任务 SQL 概览，并说明需要更精确的 pattern 或行范围 |
| sql 指定 start_line/end_line | 直接返回行范围，不执行正则，也不触发 pattern 回退 |
| start_line/end_line 超过100行 | 返回错误，不扩大返回范围 |

## 性能与限制

| 项 | 限制 |
|----|------|
| 单次查询最大返回条数 | 1000 条 |
| 默认每页条数 | task_info 20 条；sql 保留兼容字段 |
| sql_code 截取长度 | sql 仅返回匹配上下文或指定行范围；task_info 返回结构概览 |
| 单任务匹配行数 | 最多返回100个匹配行，超出后截断并提示 |
| 正则表达式超时 | 5 秒，超时后停止搜索并提示简化 pattern |
| code_path 匹配 | sql 使用精确路径；task_info 使用模糊匹配 |

### 实现建议

1. **正则匹配流程**：
   - 第一步：通过精确 code_path 从内存缓存获取单个任务
   - 第二步：使用 `regex` 库逐行执行大小写不敏感匹配
   - 第三步：根据 before/after 参数提取上下文行

2. **安全防护**：
   - pattern 参数仅用于内存正则匹配，不做 SQL 拼接（防注入）
   - 推荐使用 `regex` 库替代 `re`，支持超时控制：`regex.match(..., timeout=5)`

3. **排序逻辑**：
   - 搜索结果默认按 `project_name → process_name → task_name` 字母顺序排列
   - 也可以考虑按匹配位置排序（匹配行号小的在前）
